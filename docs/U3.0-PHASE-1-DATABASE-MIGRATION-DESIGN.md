# U3.0 Phase 1 — Database and Legacy Migration Design

**Status:** Design checkpoint for Phase 1. This is not an executable migration and has not been applied to either Supabase project.

## 1. Goals and invariants

- Add Malaysian Standard Malay (`ms`, locale `ms-MY`) without activating it before content and regression gates pass.
- Keep English (`en`) and Simplified Chinese (`zh`) fully functional during expansion.
- Preserve user IDs, saved words, collection membership and ordering, progress, activity history, session snapshots, Quiz approvals, Flashcard mastery and account isolation.
- Keep allowances shared by activity type across languages; do not create per-language quota buckets.
- Preserve timezone-local midnight resets and completion/abandonment semantics.
- Keep Dictionary search free and unlimited.
- Keep private answer keys, scoring and state transitions behind authenticated server-side RPCs.

## 2. Registry contract

Use `public.languages` as the canonical language-code registry. The application registry is a presentation/runtime mirror, not a substitute for database validation.

Recommended registry fields (retain existing columns and defaults where already deployed):
- `code` primary key (e.g. `en`, `zh`, `ms`)
- `name`, `native_name`, `locale`, `script`, `direction`
- `status` (`active`, `planned`, `disabled`)
- `capabilities` JSONB (dictionary, lessons, dailyLearning, quiz, flashcards, morphology, pronunciation, tokenisation, strokeOrder, gridMode)
- `created_at`, optional `updated_at`

Only active languages can be selected for new learning sessions. Planned languages can exist in metadata and content authoring without being selectable. The database must reject unsupported or inactive languages at the same boundary as the application.

## 3. Language-code constraint migration inventory

The Phase 0 audit identified the following en/zh-only CHECK constraints that must be reviewed and replaced by registry-backed constraints or capability-aware validation:

- `public.saved_words.course`
- `public.lesson_progress.learning_language`
- `public.lesson_practice_results.learning_language`
- `private.learning_content_catalog.language_code`
- `private.lesson_practice_attempts.learning_language`
- `private.quiz_question_bank.answer_language_code`
- `private.quiz_session_questions.answer_language_code_snapshot`
- `private.quiz_session_questions.learning_language_code_snapshot`
- `private.flashcard_cards.language_code`
- `private.flashcard_sessions.learning_language_code`
- `private.flashcard_sessions.translation_language_code`

Also verify existing registry FKs on `public.user_preferences`, `public.daily_activity_sessions.language_code`, `public.learning_activity_log.language_code`, and Quiz learning/translation language fields. Preserve FK delete/update behaviour and any existing composite keys.

Do not simply broaden every CHECK to accept any two- or three-letter string. Language codes must reference a registered language, and session creation must require the relevant feature capability.

## 4. RPC and trigger inventory

Every function below contains or participates in language-specific validation and must be reviewed before a new language is activated:

- `private.guard_lesson_progress_insert`
- `private.record_completed_lesson_practice_result_for_language_impl`
- `private.record_my_lesson_practice_attempt_impl`
- `private.start_my_chinese_quiz_impl`
- `private.start_my_quiz_impl` (all overloads)
- `private.start_my_flashcard_game_impl`
- `private.complete_my_flashcard_game_impl`
- `public.complete_permanent_lesson_for_language`

For each RPC, replace assumptions such as “zh versus everything else is English” with explicit registry/capability checks. Preserve:
- authenticated user ownership and row-level security;
- private-schema RPC-only access for protected content;
- answer-key and correct-option secrecy;
- server-side scoring and completion decisions;
- immutable session snapshots of learning/translation languages and content revisions;
- no-repeat reservations and idempotent completion;
- allowance consumption only on the established successful completion boundary;
- timezone-aware daily accounting.

Never move private Quiz answers into public content packages or browser-readable tables.

## 5. Proposed translation registry

Translation text is not the authored source record. Track translations independently by `(content_id, source_language_code, target_language_code)`, with:
- source content revision;
- translation revision;
- workflow status: `not_started`, `draft`, `machine_assisted_draft`, `legacy_unverified`, `reviewed`, `approved`, `stale`, `not_applicable`. `legacy_unverified` is migration-only and must never be treated as approved.
- provenance/source reference;
- reviewer reference and review timestamp for approval.

When source content changes, translations of the old revision become stale. Never silently overwrite a reviewed translation. Missing translations must be explicit and must not cause unrelated language text to be shown.

The first implementation may keep this registry in version-controlled content manifests and validate it in CI. If stored in Supabase, use a private table with no direct anon/authenticated SELECT; expose only the minimum approved translation payload through authenticated, purpose-built RPCs. Do not create public access to draft content or reviewer notes.

## 6. Expand → migrate → verify → contract

### Expand
1. Add/complete language registry metadata while keeping `ms` planned.
2. Add nullable or additive schema structures only; do not remove current constraints.
3. Add generic RPC versions or capability-aware implementations while preserving old signatures for existing clients.
4. Add translation and content revision metadata without rewriting existing IDs.

### Migrate
1. Backfill deterministic dictionary content IDs in version-controlled manifests; do not use display translations as IDs.
2. Keep existing lesson IDs, Daily Learning IDs, Quiz question IDs and Flashcard key formats unchanged.
3. Backfill missing language metadata only where unambiguous. Never guess a language for an unknown saved word.
4. Migrate in bounded, restartable batches and log aggregate counts only.
5. Do not copy production personal records into staging.

### Verify
- Compare row counts, distinct language codes, FK orphans, stable content IDs and per-language content counts before/after.
- Compare every existing en/zh RPC signature, grants, RLS behaviour and security definer/search_path properties.
- Test account switching, anonymous saves, account deletion, saved-word/collection order, lesson progress, Daily Learning history, Quiz snapshots/scoring/no-repeat, Flashcard mastery/session history and allowance boundaries.
- Run old-client compatibility tests while the new schema is expanded.
- Run staging tests only after migration review; no staging preview until Phase 3 is complete.

### Contract
Only after verification and release sequencing:
- switch application reads/writes to the shared registry and generic RPCs;
- activate `ms` only after its Dictionary, Lessons, Daily Learning, Quiz and Flashcard content and feature support are approved;
- remove obsolete en/zh-only checks and legacy RPCs only after no deployed client calls them.

## 7. Environment differences and release gates

Production and staging migration histories are not identical. Production has 71 migration records and staging 63, with several historical migrations named/versioned differently and five audited table-definition differences. Never replay migrations based only on migration count or name. Compare actual table definitions, constraints, indexes, triggers, function definitions, grants and policies in each project.

No SQL migration has been executed or added to the active migration directory in this Phase 1 checkpoint. Before implementation, create environment-specific forward migrations only after reviewing each environment's actual schema. Live Supabase migration must precede any frontend release that depends on it. Keep rollback/forward-repair scripts and post-migration aggregate verification queries with each migration.

## 8. Data provenance and Malaysia legal planning

- New Malay content must have an explicit source/authorship and licence record before inclusion.
- Re-audit provenance of the older English baseline/expansion, original Chinese base entries and pre-existing lesson examples; current notices do not automatically clear older material.
- Keep CC-CEDICT-derived Dictionary content free and unrestricted, with CC BY-SA attribution/share-alike obligations.
- Review Malaysia PDPA applicability, notices, controller/processor roles, data retention/deletion, cross-border transfer safeguards (production Tokyo, staging Singapore), incident handling and any DPO/registration obligations before public Malay launch.
- Review general international privacy requirements for the global audience. This is planning, not legal advice or legal clearance.

## 9. Current implementation coverage

The feature branch now includes:
- runtime language registry and language-specific adapters;
- shared content contracts and package wrapper for the legacy English/Chinese Dictionary and Lessons data;
- explicit Daily Learning language dispatch and package data export;
- strict Flashcards/Daily Learning behaviour for unimplemented languages (no silent English fallback);
- registry-based saved-word language checks in local state, Collections and anonymous account deletion;
- shared locale-aware Quiz validation primitives, while preserving pair-specific curriculum and linguistic rules.

This is still not a production database migration. A local architecture/integration run passed 22 Node tests, and application script dependency order plus language-manifest activation states were checked against the feature branch. The complete Phase 1 exit gate is still open until the full browser/device regression matrix, content/package count parity, account/progress/allowance history parity, and environment-specific database compatibility review are evidenced. No staging preview is permitted before Phase 3 completion.
