# U3.0 Phase 3 — Malay learning database and release impact

**Date:** 2026-11-27  
**Status:** Design/impact assessment only; no SQL migration has been applied or added to the active migration directory.  
**Application branch:** `feature/update-3.0-phase-0-audit`

## 1. Current Phase 3 application scope

The feature branch now contains the initial Malay Lessons and Daily Learning content pack. The language registry and manifest enable Malay only in this isolated branch for Dictionary, Lessons and Daily Learning. Quiz and Flashcards remain unsupported and are explicitly blocked in the UI until their later phases.

The first content batch contains 9 lessons (3 per difficulty), 3 Daily Topic activities, 3 Daily Application activities and a 93-entry Daily Discovery rotation. Daily Revision reuses the adaptive review selector and Malay application topics. All new content and support translations are marked draft and are not human-approved.

## 2. Database compatibility blockers

The existing U2.7/U2.8 migration history has explicit `en`/`zh` allowlists. A front-end-only language activation is not sufficient for reliable learner progress.

The reviewed U2.7 language-aware lesson migration contains these direct blockers:

- `public.lesson_progress.learning_language` CHECK currently accepts only `en` and `zh`.
- `public.lesson_practice_results.learning_language` CHECK currently accepts only `en` and `zh`.
- `private.learning_content_catalog.language_code` CHECK currently accepts only `en` and `zh`.
- `private.guard_lesson_progress_insert()` rejects every language except `en` and `zh`.
- `public.complete_permanent_lesson_for_language(...)` rejects every language except `en` and `zh`.
- `public.record_completed_lesson_practice_result_for_language(...)` rejects every language except `en` and `zh`.
- The approved-content guard requires a matching active `permanent_lesson` row in `private.learning_content_catalog`; the nine Malay lesson IDs/topics are not yet seeded there.

The Phase 1 database design also identifies registry/FK compatibility to verify for `public.user_preferences`, `public.daily_activity_sessions.language_code` and `public.learning_activity_log.language_code`. The actual staging and production schemas differ; do not infer compatibility from migration names or migration counts.

## 3. Required staging-only migration design

Before a staging review can test saved Malay progress end to end, prepare an environment-specific additive migration that:

1. Verifies the actual staging schema, constraints, indexes, triggers, functions, grants, RLS policies and registry rows.
2. Adds `ms` to the registered language catalogue with Malaysian Standard Malay metadata, while keeping capability checks explicit.
3. Extends only the required lesson-progress and practice-result constraints to include the registered `ms` code.
4. Updates the lesson insert guard and language-aware completion/replay RPCs to validate the registered language and the appropriate Lessons capability rather than treating every non-`zh` language as English.
5. Adds the 9 Malay permanent lesson IDs, topic IDs and difficulty levels to `private.learning_content_catalog` as draft/review-required staging records. Do not label them approved merely to bypass the existing release guard.
6. Confirms that `daily_activity_sessions` can store `ms` as a registered language while the four daily allowance categories remain shared across languages and continue charging only on successful completion.
7. Preserves all existing English/Chinese rows, unique keys, progress, account isolation, history, and timezone-based allowance behaviour.
8. Includes post-migration verification and a tested forward-repair/rollback strategy appropriate to the staging schema.

**Important release-design question:** the current approved-content guard may not permit draft catalogue rows to start lessons. Before staging, choose a safe staging-only release state or capability gate that permits the owner to test draft content without making it publicly approved. Do not weaken the production approval guard.

## 4. Approval boundary

A staging migration requires a separate explicit owner approval after the environment-specific diff and SQL review. Production remains untouched.

## 5. Legal, privacy and content-rights review

- The Phase 3 UI reuses existing account-bound lesson progress, practice-result, daily-session and allowance mechanisms. It does not intentionally add a new personal-data field or third-party processor. Confirm actual database writes and privacy-notice coverage before staging.
- Adaptive Daily Revision uses recent topic-level practice accuracy to prioritise review. Keep the logic explainable to learners, avoid sensitive inference, and review whether existing privacy disclosures adequately describe adaptive learning/profiling.
- Malaysia's PDPA Amendment Act 2024 has phased commencement dates in 2025. Before public launch, check the current Commissioner's requirements for data-controller registration, DPO appointment, breach notification and cross-border transfers, particularly given the use of hosted authentication/database services. See the official [PDPA Amendment Act 2024 page](https://www.pdp.gov.my/en/akta/personal-data-protection-amendment-act-2024/) and the Commissioner's [2026 Circular No. 1 on registration of data controllers](https://www.pdp.gov.my/en/akta/personal-data-protection-commissioners-circular-no-1-2026-registration-of-data-controllers/).
- All Malay Dictionary entries, machine-assisted English/Chinese translations and new learning content remain draft. The staging review must record actual reviewers, source references, rights status and decisions. Do not reproduce protected DBP/PRPM/Kamus Dewan material without a valid licence or permission.

- Existing Quiz and Flashcard tables contain additional `en/zh` checks. These remain Phase 4/5 work and must not be changed as part of the Phase 3 staging migration unless a shared dependency is demonstrated.

### Updated staging-only migration scope

The environment-specific migration design must account for:
1. Add `ms` to the staging `public.languages` registry, without touching production.
2. Extend the lesson progress, practice-result and practice-attempt language checks to accept `ms`.
3. Update the lesson insert/completion/replay guard path to validate the registered course and exact active catalogue identity, while retaining authentication, account ownership, advisory locking, aggregate-result bounds and approved-content checks.
4. Extend `private.learning_content_catalog.language_code` for `ms` and seed staging-only records for the 72 permanent lessons, 60 Daily Topics, 60 Daily Applications and 93 Discovery entries. Preserve the existing discovery rotation contract. The catalogue uses active status as the runtime approval gate, so the staging-only draft release must be isolated to the staging project and must not weaken the production guard.
5. Extend `saved_words.course` to include `ms` if dictionary save/sync is part of the preview acceptance path.
6. Verify daily sessions, activity log, preference foreign keys, shared allowance categories and timezone reset. No new language-specific allowance buckets.
7. Preserve all English/Chinese records and user progress; include pre/post row counts, security/RLS review, rollback/forward-repair plan and post-migration tests.

The existing Phase 3 report's initial nine-lesson/three-topic/three-application inventory is historical; the final feature-branch content inventory is now 72 Lessons, 60 Topics, 60 Applications and 93 Discovery entries.

**Approval boundary remains unchanged:** this is a read-only assessment and migration-design update only. Explicit owner approval is required before applying any staging DDL or seed data. Production remains untouched.
